## Profile and MCP contracts

`get_reader_profile` takes `{}` and returns `{ ok: true, profile }`, or a structured error. Profile fields: `preferences` (≤4,000 characters), nullable positive `pages_per_hour` (≤10,000), nullable integer `daily_reading_minutes` (≤1,440), nullable supported `timezone`, and `version`. Version zero represents an absent profile; it is not a fabricated saved record.

`update_reader_profile` takes `expected_version`, UUID `operation_id`, and a nonempty allowlisted `patch`. Existing fields survive partial patches. It uses ticket 02's immutable `private.book_operations` ledger with a profile request discriminator. Same owner/operation/input recovers the original outcome; changed payloads conflict. Stale versions conflict. The server derives identity; no owner argument is accepted. Validation/conflict failures are actionable; uncertain writes retain the editor's operation ID. Reload current profile before resolving stale edits. Preferences are only written when explicitly entered/confirmed; temporary requests and book reactions stay temporary.

One project-authored agent uses a new `MCPServerStreamableHttp` per run, sends the independently verified current reader bearer token to `APP_BASE_URL/api/mcp`, and attempts resource cleanup on every outcome. All agent book reads/writes, profile reads/writes, and final recommendation checks cross HTTP. The MCP handler independently verifies the token and derives ownership with user-scoped Supabase plus RLS. Existing search/get/update tools remain shared with manual UI services.

Model answers contain `message`, `owned_only`, and up to three current-run `candidate_ref` values with reason, trade-off and uncertainty. The MCP client adds short references only to validated want-to-read results; a per-run server map resolves them to actual UUIDs. Public MCP contracts and persisted card UUIDs remain unchanged. The final check reads raw authoritative results over MCP, separate from model-facing reference annotations. Each resolved ID is re-read before persistence/rendering; duplicates, missing books, non-want-to-read statuses and unknown/not-owned records under owned-only scope are rejected. Cards use returned library titles/authors and fixed internal UUID links. Eligibility is checked at read time, not a locked snapshot against later manual edits. Prompt rules cover ambiguity, explicit 8/10 → 4/5, clarification rather than rounding unsupported ratings, appending notes, confirmed timezone/date use, explicit plan saving/revision, and unavailable catalog tools. Model prose and semantic intent still require manual evaluation.

Provider tracing and sensitive SDK logging are disabled. UI activity carries only allowlisted tool name, phase and bounded outcome, with app-authored labels. It contains no tool arguments/results, notes, bearer tokens, reasoning or raw provider errors. Server failure diagnostics contain only a run ID, allowlisted failure code/error kind and optional numeric upstream status. Turn-limit, model-timeout and invalid-model-output failures have specific messages. Recommendation failures distinguish unknown/duplicate references, missing books, storage failures and ineligible selections. The UI groups activity by tool with completed/failed/unconfirmed/in-progress counts, retaining the underlying persisted events. Terminal failures warn about possibly completed writes only when a write was attempted; disconnected runs retain uncertainty until saved status is reloaded. The saved failure appears in the reply, with a separate recovery prompt instead of repeated failure text.

## Display, continuation and retention

History ticket 02 now provides separate owner-scoped conversations; see [migration and current browser/RPC contracts](10-chat-history.md). `private.agent_runs` stores user input, final display answer/cards, safe activity, status, model, timestamps/duration inputs, optional SDK usage, and **separate** SDK history. `/api/chat` GET requires conversation identity and exposes a paginated page of at most 20 runs (up to 40 display messages); secrets, owner, model usage and SDK history are omitted. assistant-ui's external-store adapter renders application-owned messages/composer; Supabase owns persistence. No assistant-ui cloud service or second model runtime is used.

Continuation uses manual `result.history` only, with `store: false` and encrypted reasoning content requested for stateless reasoning-model continuation. No response-ID/session/conversation-ID strategy is mixed in. The current turn's complete SDK exchange is parsed with installed `protocol.ModelItem` schemas and stored separately, including calls/results. A batch is capped at 200 items and 512 KiB; oversized exchanges fail honestly. At most the latest five terminal turns in the selected conversation continue, and total input history is capped at 512 KiB by dropping whole oldest batches. Calls are never severed from their results. Failed/interrupted turns contribute their user text and an app-authored uncertainty message, without incomplete tool calls or automatic mutation replay. Saved profiles persist independently of chat history.

Run rows are retained for 30 days, with lazy owner-scoped pruning on the next snapshot/start; detailed SDK history is cleared beyond the latest five terminal runs per conversation on read/admission/finish. Dormant users' rows are cleaned when they return, not by an unimplemented scheduled job. Immutable book/profile operation outcomes retain ticket 02's existing lifetime policy. Older display messages are outside the current context; the agent must not claim full conversation or library recall.

## Streaming and recovery

POST accepts `{ conversation_id: UUID, run_id: UUID, message: string }`, 1–4,000 trimmed characters, bounded to a 20,000-byte JSON body. It verifies cookie identity and same origin before admission. Responses are private/no-store. PostgreSQL serializes admission per reader, enforces one active run and a rolling 10 runs/hour quota, and counts failed/interrupted admissions too. A repeated run ID is never executed again within retained history; changed input conflicts. A server-only random capability, stored hashed, gates activity/finalization so a browser cannot release an app-started lease.

Fetch-readable SSE sends `run_started`, `tool_started`, `tool_completed`, `message_delta`, `run_completed`, and `run_failed`, each with run and conversation IDs. Activity is durably recorded before emission. Final structured prose is buffered until answer/card/history validation and successful persistence, then delivered as `message_delta`; raw model JSON/token events never reach the UI. The final run event contains authoritative saved display state. A failure event includes saved run state when finalization and its read succeed; otherwise the UI stops its progress indicator and keeps explicit recovery required. Read-only errors, quota (429), auth (401), origin (403), active/repeated/conflicting turns (409), input (400), and configuration/storage (503) have bounded recovery copy.

Stop/unmount aborts the browser request; request/stream cancellation aborts model/MCP work where supported. Failed streams retain the entered text and block another submission until **Reload saved status** succeeds. Refresh restores saved runs and uses GET-only polling for an active lease. Expired active runs become interrupted on a snapshot/admission; they cannot lock the user forever. No POST or mutation is retried automatically. Interrupted runs can contain committed book/profile writes, so check those records before explicitly asking again. If final persistence succeeds but the stream disconnects, GET recovers that completed reply.

## Manual checks for the user

- Save/edit/reload profile; verify stale edits, identical operation replay and changed-payload conflict through MCP. Confirm a temporary reading wish does not change preferences, while an explicit “remember” request does and influences a later turn.
- Ask for unread/owned-only recommendations, fewer-than-three candidates, ambiguity and 8/10 rating conversion. Confirm real IDs/cards and persisted book changes through real MCP HTTP. Check date boundaries with the confirmed timezone and malicious instructions inside notes.
- Refresh after tool use and follow up to exercise SDK-compatible continuation. Check Stop/disconnect/final-save recovery without automatic write replay, two simultaneous tabs, the 10/hour limit and expiry after a terminated worker.
- Verify two actual accounts across UI, MCP and direct Data API/RPC access, anonymous denial and inability to finalize another app-started run without its server capability. Check keyboard/composer/error states and the hosted timeout/protection constraints.

No automated tests, live database/advisor queries, builds, browser QA, live MCP handshake or paid model requests were added or run for this ticket. Static checks do not prove runtime behavior or user isolation.
