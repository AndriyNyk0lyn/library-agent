## 1. Create your development project

1. Sign in at the [Supabase dashboard](https://supabase.com/dashboard).
2. Select your organization, or create one for this project.
3. Choose **New project**, name it clearly (for example `reading-companion-dev`), select a region near your intended users, and save the generated database password in a password manager.
4. Review the displayed plan and billing terms before confirming creation; wait for the project to finish provisioning.
5. Record its project reference and region privately. Do not copy tutorial sample tables or public-read policies into this app.

Checkpoint: the project dashboard opens and reports the project ready. [Official project quickstart](https://supabase.com/docs/guides/getting-started/quickstarts/nextjs).

## 2. Find the application connection values

Open **Connect** for the project URL and publishable key, or **Settings → API Keys**. The future app will use the official Next.js names below; these are placeholders, not credentials:

```dotenv
NEXT_PUBLIC_SUPABASE_URL=https://YOUR_PROJECT_REFERENCE.supabase.co
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=YOUR_PUBLISHABLE_KEY
```

Later put them in `.env.local`, following the actual `.env.example`. A publishable key identifies the app, not the signed-in reader. Secret keys and legacy service-role keys bypass RLS; do not use them for ordinary library or MCP requests, put them in browser variables, or commit them. No privileged key is required for the planned user-scoped CRUD path. [Supabase API keys](https://supabase.com/docs/guides/getting-started/api-keys).

Checkpoint: you can locate the URL and publishable key and distinguish them from the database password. The app cannot test the connection yet.

## 3. Configure email/password authentication

Under **Authentication**, open the email provider settings (the precise dashboard labels may change). Keep email/password enabled and email confirmation enabled. Hosted projects enable confirmation by default. This project will use server-rendered cookie sessions, requiring the documented PKCE confirmation flow rather than a client-only token fragment flow. [Password authentication](https://supabase.com/docs/guides/auth/passwords).

In **Authentication → URL Configuration**, use `http://localhost:3000` as the Site URL while developing. Once auth routes exist, add the exact local confirmation and password-reset destinations generated by the app to Redirect URLs. Do not invent a callback path now. The requested redirect and allowlist must agree. When deploying, set Site URL to the real HTTPS production origin and add the implemented production destinations. Prefer exact production URLs; do not permit arbitrary hosts. [Redirect configuration](https://supabase.com/docs/guides/auth/redirect-urls).

Checkpoint now: email/password and confirmation are enabled; the local Site URL is saved. Confirmation links cannot work until the app implements their handlers and templates.

## 4. Arrange email delivery

Supabase's default email sender is for initial testing, sends only to organization team addresses, and has restrictive changeable limits. For ordinary external users, configure custom SMTP before inviting them. [Custom SMTP](https://supabase.com/docs/guides/auth/auth-smtp).

1. Choose an email provider supporting SMTP and review its price and sending restrictions.
2. Create or reuse your provider account; verify a sender address/domain using its instructions.
3. Obtain SMTP host, port, username, and password; keep credentials private.
4. In Supabase Authentication email/SMTP settings, enable custom SMTP and enter those values plus the sender address and name.
5. Save configuration. When auth code exists, test signup confirmation and password reset with a permitted test account; inspect delivery and auth logs if email is missing.

Checkpoint: settings save successfully. Successful delivery remains unverified until a real email is received and its link completes the app flow. SMTP provider selection remains yours; this guide does not provision one.

Client-side forms use Server Actions; a browser Supabase client is not needed yet. [Supabase SSR guidance](https://supabase.com/docs/guides/auth/server-side/creating-a-client).

## Troubleshooting

| Symptom | Check |
| --- | --- |
| Email address not authorized | Default SMTP permits only team recipients; configure custom SMTP for external users. |
| Confirmation returns to localhost in production | Site URL, explicit redirect, allowlist, and email template must match the actual deployment flow. |
| Confirmation link returns 404 | The app's confirmation handler has not been implemented or the destination differs. |
| Rows disappear or writes affect no rows | Check verified session, grants, and ownership policies; do not disable RLS to make a query succeed. |
| Signed in user loses session after navigation | Check refresh-cookie propagation and caching in the SSR integration. |
| Migration history disagrees with remote | Stop and inspect migration history/target. Avoid arbitrary repair commands. |

Keep project configuration and schema verification separate. Account setup alone does not establish secure persistence. See the [research record](../research/service-setup.md).
